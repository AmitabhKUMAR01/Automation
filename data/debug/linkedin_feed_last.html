    Cloudflare D1 vs Turso comes up a lot, and this Code Story piece cuts through the marketing well: https://lnkd.in/gUPECQup Thanks Noah Labhart

    The core framing: D1 reduces integration work when Cloudflare is already your runtime. Turso reduces runtime dependence when your database needs to serve multiple deployment models.

    A few specifics worth knowing:

    D1 is single threaded per database, so a database averaging 100ms queries tops out around 10 QPS. Turso's engine handles concurrent writes.

    D1 caps every database at 10GB, and that limit can't be increased. Real constraint if you're doing database per tenant at scale.

    Turso ships native SQL vector search. On D1 you need a separate service (Vectorize) for that.

    Free tier: Turso gives 100 databases and 500M monthly row reads. D1 gives 10 databases and 5M daily row reads.

    D1 isn't bad, if you're all in on Workers and mostly read heavy, it's a solid fit. But for multi runtime apps, high write concurrency, or database per tenant patterns, the tradeoffs favor a different architecture.

    As the article puts it: the best many database platform is the one your team can operate safely, not the one with the biggest published limit.

    If you have ever tried using a traditional relational database alongside serverless functions, you know that infrastructure usually becomes a problem quickly.

    The bottleneck is almost always the time the application takes to open database connections or the connection pool maxing out when there are many simultaneous requests.

    Turso was created to solve this in a very straightforward way: it took SQLite and transformed it into a database for the cloud.

    Its architecture is based on libSQL, an open-source fork of SQLite. SQLite is known for being unbeatable in local development because it runs entirely within a single file, without the need to configure heavy servers. What Turso did was take this same lightweight structure and create a system to replicate these database files on the "edge" — meaning, spreading the data across multiple servers around the world.

    When a user makes a request, the read happens on the server physically closest to them, which drives latency way down.

    The major technical difference is that, instead of relying on continuous TCP connections like PostgreSQL, Turso communicates via HTTP and WebSockets. For a serverless application, whose functions are born and die in milliseconds, this is the ideal format. The application makes the request, receives the data, and ends the process, without leaving dangling connections on the server.

    The financial and architectural model also changes. Since each database in Turso is basically a lightweight file, you don't need to pay for a server instance running idle 24 hours a day. It is feasible and cheap to create thousands of simultaneous databases. You can provision an entire, separate database for each client on your platform. If a project is compromised, the breach remains isolated to that specific database.

    In short, Turso delivers the same frictionless experience we get when programming locally with SQLite, but with the distributed scalability needed to put a modern application into production.

      Calling Turso a “rewrite of SQLite” is accurate, but it can give the wrong impression.

      This wasn’t a line-by-line translation of SQLite into Rust. Turso is a ground-up reimplementation with an entirely different engine underneath.
      It remains compatible with SQLite at the SQL dialect, file-format, and C API levels, while its modern architecture supports capabilities such as async I/O and concurrent writes.

      Turso is already running in production, although it has not reached 1.0 and some compatibility gaps remain.
      It’s SQLite-compatible from the outside, but very different on the inside.

        Wrapping up my 3-part series on SQLite encryption today.

        Part 1 looked at why SQLite doesn't ship with encryption and what developers actually reach for instead. Part 2 walked through         Turso's two encryption models, native engine encryption for local/embedded deployments and BYOK for Turso Cloud, with working code and benchmarks.

        Part 3 is the one most teams actually need, because turning encryption on is the easy part. This one covers what happens after:

        -Key management: generation, storage, and rotation, and why "just use Math.random()" is still the #1 way encryption fails in production

        -Migration paths from SQLCipher, SEE, or plain unencrypted SQLite, with a checklist for validating the move

        Part 2 of the series: once you know why SQLite needs encryption, the next question is how to actually do it. Here's how we approached it at Turso, and why we ended up with two different models instead of one.

        Turso Database (the local, Rust based engine) has native encryption built into the core, not bolted on as an extension. It's still marked experimental, gated behind a flag, because we'd rather be upfront about where it sits in the audit process than call it done before it is. You generate a 256 bit key, pass it in the connection string, and choose your cipher (AEGIS is our recommendation, AES-GCM is there for compliance heavy environments). Overhead runs as low as 0.5% on mixed workloads.

        Turso Cloud takes a different approach: BYOK. We never store your encryption keys. They exist in memory only for the duration of a query. If our storage layer were ever compromised, an attacker gets ciphertext and nothing else. This is now self-service on the Pro plan and above, and it works alongside branching, point in time recovery, and embedded replicas.

        The part I think matters most for multi-tenant SaaS: because Turso has no practical limit on the number of databases you can run, you can give every customer their own encrypted database with its own key. That's real cryptographic isolation, not row level access control with a shared key underneath it. One compromised customer doesn't put every other customer at risk.

        We're upfront about what's not there yet too. Key rotation isn't native yet, so today it means export and reimport, which means downtime. Worth knowing before you build around it.

        Full details, code examples, and cipher benchmarks here: https://lnkd.in/gimDjNbv

        SQLite doesn't ship with encryption. That's not an oversight, it's a deliberate design choice: the SQLite team has always treated encryption as an OS or filesystem concern, not a database concern.

        But that leaves developers to figure it out on their own. This is part 1 of a 3 part series where I dig into what's actually out there.

        SQLCipher has been the default answer since 2008. It works, but major version upgrades come with painful format incompatibilities, and it's built around a single cipher (AES-256-CBC).

        SQLite Encryption Extension (SEE) is the official option from the SQLite team, but it's proprietary and closed to independent security audits, which makes it a hard sell outside enterprise procurement.

        SQLite3MultipleCiphers emerged after SQLite quietly removed the undocumented SQLITE_HAS_CODEC hook in 2020, breaking every third-party encryption extension overnight. It's actively maintained and a good bridge for legacy databases.

        All three were designed for a single user, single database world. They weren't built for BYOK models, multi tenant SaaS with millions of individually keyed databases, or modern ciphers like AEGIS. That gap is why we built native encryption into         Turso, with page level AEAD encryption and about 1% overhead.

        If you're maintaining a stable SQLCipher deployment, there's no reason to migrate. But if you're starting something new or hitting these limits, it's worth a look at what's changed.

        Full breakdown here: https://lnkd.in/gyN-z5Mz
